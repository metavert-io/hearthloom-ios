# hearthloom-ios — developer guide

Native SwiftUI client for a Hearthloom node. Phone = authenticated client +
on-device adapter host (never a peer). Project generated by **xcodegen**
(`project.yml` is the source of truth; the `.xcodeproj` is gitignored — run
`./Scripts/generate.sh` after editing `project.yml`). The node API the app
calls is in `docs/node-api.md`.

Self-hosting comes first: the Connect screen leads with pairing and a server
address; a hosted provider is only ever a listed option (build settings
`HEARTHLOOM_PROVIDER_NAME` / `HEARTHLOOM_PROVIDER_URL`), never a default. Keep
personal or deployment details (team IDs, hostnames, tokens, people) out of the
repo: they belong in gitignored local files.

## Signing & device install
- **Signing is per developer.** `Config/Signing.xcconfig` (committed: empty
  `DEVELOPMENT_TEAM`, bundle ID `org.example.hearthloom`) is wired into every
  target through `configFiles:` in `project.yml` and includes the gitignored
  `Config/Signing.local.xcconfig` last (template:
  `Config/Signing.local.xcconfig.example`). Bundle IDs derive from
  `$(HEARTHLOOM_BUNDLE_ID)` (+ `.controls`, `.tests`, `.uitests`). Never put a
  team or bundle ID under `settings` in `project.yml`: those override the
  xcconfig. Check with `xcodebuild -showBuildSettings | grep -E 'TEAM|BUNDLE'`.
- **`xcodegen generate` OWNS `Sources/Hearthloom/Hearthloom.entitlements`** and
  rewrites it to an empty `<dict/>` on every run unless the entitlement is
  declared under `targets.Hearthloom.entitlements.properties` in `project.yml`.
  HealthKit (`com.apple.developer.healthkit`) is declared there — do NOT hand-edit
  the entitlements file expecting it to stick (it silently strips HealthKit from
  device builds; caused a "missing entitlement" crash 2026-07/08).
- **HealthKit on device also needs the App-ID capability registered** (one-time,
  Xcode GUI → target → Signing & Capabilities → + Capability → HealthKit).
  Headless `-allowProvisioningUpdates` can't toggle App-ID capabilities.
- **A new device must be registered once via Xcode GUI** (Signing tab / Devices
  window) before CLI signing includes its UDID; otherwise install fails with
  "provisioning profile cannot be installed on this device."
- **CLI build + install recipe** (wireless, phone unlocked + Developer Mode on):
  ```
  ./Scripts/generate.sh    # (was: xcodegen generate) — keeps Sentry/other overlays
  xcodebuild -project Hearthloom.xcodeproj -target Hearthloom -configuration Debug \
    -sdk iphoneos -allowProvisioningUpdates \
    CODE_SIGN_STYLE=Automatic CONFIGURATION_BUILD_DIR="$PWD/build/device" build
  xcrun devicectl device install app --device <devicectl-id> build/device/Hearthloom.app
  ```
  Wireless installs flake ("tunnel reset"/timeout) — just retry a few times.
  Verify HealthKit embedded: `codesign -d --entitlements :- build/device/Hearthloom.app`.

## Project generation — use `./Scripts/generate.sh`, not bare `xcodegen`
`Scripts/generate.sh` runs xcodegen and layers in any opt-in **feature overlays**
that exist locally (currently just Sentry). With no overlays it's identical to
`xcodegen generate`. A default clone therefore builds with none of the optional
features. Overlays merge via a composed root spec (`include: [project.yml, …]`);
remember array keys (`dependencies`) concatenate but dict keys (`info.properties`)
do NOT deep-merge across includes — route per-feature values through
`settings.base` (which does merge) + a `$(VAR)` reference in the base Info.plist.

## Sentry APM (optional — OFF by default, opt-in overlay)
Nothing Sentry ships in a default clone: no SPM package, no code (Observability.swift
is `#if canImport(Sentry)`-guarded), and Info.plist's `SENTRY_DSN` = `"$(SENTRY_DSN)"`
resolves to `""` (build setting undefined) → `Observability.start()` early-returns.
- **Enable:** `cp project.sentry.yml.example project.sentry.yml` (gitignored), paste
  your DSN, then `./Scripts/generate.sh`. The overlay adds the Sentry package +
  dependency and sets the `SENTRY_DSN` build setting, which flows into Info.plist.
- **Disable again:** delete `project.sentry.yml` and re-run the script.
- DSN is a client-side send-only key; it's kept out of git by convention, not
  because it's secret. Bootstrap: `Services/Observability.swift` ← `HearthloomApp.init()`.
- **Crash symbolication (dSYM upload):** the overlay forces
  `DEBUG_INFORMATION_FORMAT = dwarf-with-dsym` for Debug (default is dwarf-only →
  no dSYM → unsymbolicated crashes from the Debug builds we sideload) and adds a
  `postBuildScripts` phase that runs `sentry-cli debug-files upload`. The phase
  no-ops (exit 0) if `sentry-cli` or `.sentryclirc` is missing, so it never breaks
  a build. Auth token/org/project live in the gitignored `.sentryclirc`
  (template: `.sentryclirc.example`). The token IS a real secret (unlike the DSN).

## Git / secrets
- Commit/push only when asked.
- Never commit tokens. `secrets.local.*`, `*.pat`, `.sentryclirc`,
  `project.sentry.yml` and `Config/*.local.xcconfig` are gitignored; live tests
  read their node and token from `TEST_RUNNER_…` environment variables.

## Device-adapter pattern (health, photos, contacts, calendar, …)
Each adapter: on-device source → incremental marker/anchor → chunked POST via the
shared `IngestGate` (serializes ALL device uploads) → gated by
`<X>IngestConfig.streamingEnabled` until the server endpoint ships → owned by the
app-level `DeviceAdapters` (ShellView), auto-resumed on launch/foreground when
`<X>.isEnabled`. Idempotency is per-source (server dedups); cross-source LOCATION
dedup is server-side (`docs/node-api.md`, "Device ingest"). New adapters
reuse `HearthAPI.postIngest` + the `DeviceAdapter` protocol + `AdapterView`.

## Quick capture (differs from the adapter pattern)
`CaptureToHearthloomIntent` (Siri / Shortcuts / Action Button) runs in the
background with NO user present, so it can't use the biometric-gated device token.
It uploads with a capture-only scoped key in `CaptureKeyStore` (after-first-unlock;
never put the device token there), minted with grants `{capture, own_device}` so
the node records captures as the owner's own words. Queue-first (`CaptureQueue`, a file), drained by
`CaptureService` through `IngestGate`. No `streamingEnabled` flag: a 404 from the
node is the gate. The control lives in the `HearthloomControls` extension (min iOS
18, no entitlements); its `OpenCaptureIntent` is in `Sources/Shared` and MUST stay
in both targets or the control stops opening the app. Live tests need a throwaway daemon:
`TEST_RUNNER_HLIOS_CAPTURE_LIVE_URL` / `_PAT` (unit), `TEST_RUNNER_HLIOS_BASE_URL`
/ `TEST_RUNNER_HLIOS_PAT` (UI).

## Tests
```
xcodebuild test -project Hearthloom.xcodeproj -scheme Hearthloom \
  -destination 'platform=iOS Simulator,name=iPhone 17'
```
Unit tests and the offline UI tests (`ConnectScreenUITests`,
`CaptureControlUITests`) need no node. The live tests skip unless their
environment variables are set — point them at a throwaway node, never one with
data you care about.
